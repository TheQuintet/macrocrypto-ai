# Grading & Pass Criteria

How the Capstone is scored, what we need to **pass**, and what to aim for to get the **best score**.

> When in doubt, follow official course materials in your Studio tab. This page is a team reference.

---

## Scoring scale

| Score | Meaning |
|-------|---------|
| **5** | Exceptional — portfolio-quality, strong engineering, polished delivery |
| **4** | Strong — complete project with minor gaps in polish, testing, or documentation |
| **3** | **Pass** — meets all requirements; acceptable quality |
| **2** | Below pass — missing depth, weak deliverables, or partially broken submission |
| **1–0** | Failing — major missing deliverables, non-working product, or integrity issues |

**Pass threshold:** **3 or higher** (on a 0–5 scale).

---

## Pass criteria (minimum requirements)

To be eligible for a passing score, we must complete **all** mandatory deliverables and follow program rules.

### Mandatory deliverables

| # | Deliverable | Must have |
|---|-------------|-----------|
| 1 | [GitHub repository](./deliverables.md#1-github-repository) | Documented code, shared with `quantic-grader`, all 6 members contributed |
| 2 | [Deployed application](./deliverables.md#2-deployed-application) | Publicly accessible (web apps), stable enough to demo |
| 3 | [Design & testing document](./deliverables.md#3-design-and-testing-document) | Architecture, patterns, testing approach — written **manually** |
| 4 | [Agile task board](./deliverables.md#4-agile-task-board) | At least **3 sprints**, user stories/tasks, work matches what we built |
| 5 | [Video presentation](./deliverables.md#5-video-presentation) | 15–20 min; working demo; every member speaks, is on camera, shows government ID |

See [Deliverables](./deliverables.md) for the full checklist.

### Process requirements

- [ ] **Product Owner** and **Scrum Master** assigned — [Team](../team-roles.md)
- [ ] **Agile** followed: 3+ sprints, task board, ceremonies — [Agile & Sprints](../project-workflow.md)
- [ ] **Planning** and **refinement** sessions documented — [Planning](../meetings/templates/planning.md) · [Refinement](../meetings/templates/refinement.md)

### Policy requirements

- [ ] **Academic integrity** — cite external code and sources; no plagiarism — [Policies](./policies.md)
- [ ] **AI policy** — AI for code encouraged; written docs must be our own words; cite AI influence

Missing any mandatory deliverable or violating integrity rules can result in a score **below 3**, regardless of product quality.

## How to aim for the best score (4–5)

The program expects a **high-quality portfolio piece** — not just a basic web app. Top scores reward teams that meet every requirement **and** demonstrate strong engineering judgment.

### 1. Build something that stands out

- Clear **problem → solution → user value**
- More than a CRUD demo: meaningful features, thoughtful UX, or real AI/engineering depth
- Ambitious but **finished** — a polished smaller product beats an unfinished large one

### 2. Show real software engineering

- **Architecture** — layers, APIs, data model; explain *why* we chose them
- **Patterns** — used appropriately (e.g. repository, MVC, event-driven)
- **Code quality** — readable structure, naming, separation of concerns
- **README** — someone unfamiliar can clone, run, test, and deploy

### 3. Testing (often a big differentiator)

- **Automated tests** on critical paths
- Clear split: unit vs integration vs manual testing
- Tests run easily (locally or in CI)
- Design doc explains **what** we test and **why**

### 4. Professional delivery

- Deployed app **works** at grading time
- No broken links, missing env setup, or secrets in git
- Repo history shows **real collaboration** (PRs, reviews, balanced commits)

### 5. Strong Agile evidence

- 3+ sprints with clear goals and outcomes — [Agile task board URL](./deliverables.md#4-agile-task-board) + [Agile & sprints](../project-workflow.md)
- User stories with **acceptance criteria**
- Task board matches repo and demo — no fiction
- Planning and refinement notes kept up to date
- Retrospective evidence: [Sprint 2 retro board + notes](../meetings/2026-08-05-sprint-2-to-3-retrospective.md); later improvements in [meeting notes](../meetings/) — see [how we ran retrospectives](../project-workflow.md#retrospective)

### 6. Excellent documentation

- Design doc shows we understand the system end-to-end
- Explains trade-offs (“we chose X over Y because…”)
- Architecture / data-flow diagrams where helpful
- AI influence cited honestly where relevant — [AI-assisted development disclosure](../ai-assisted-development-disclosure.md)

### 7. Strong video presentation

Minimum = everyone speaks + ID on camera. **Top scores** usually also include:

- Clear narrative: problem → approach → demo → testing → lessons learned
- Smooth demo of **core user flows**
- Each member presents **their area** (backend, frontend, AI, testing, etc.)
- Rehearsed, 15–20 minutes, good audio and video

## Team checklist — aim for top score

### Product

- [ ] One clear user problem; demo proves we solved it
- [ ] Core flow works end-to-end on the **deployed** URL
- [ ] At least one impressive element (AI, automation, non-trivial logic, strong UX)

### Engineering

- [ ] Clean repo structure and strong README
- [ ] Design doc with architecture diagrams and decision rationale
- [ ] Automated tests on important behavior
- [ ] `quantic-grader` has repo access; no secrets committed

### Process

- [ ] Product Owner and Scrum Master named
- [ ] 3+ sprints on board; stories match shipped work
- [ ] Planning and refinement session notes maintained

### Submission

- [ ] All 5 deliverables submitted on time
- [ ] Video: 15–20 min; all 6 members speak, on camera, with ID
- [ ] Design doc manually written; AI cited where used

### Integrity

- [ ] No plagiarized code; external sources cited
- [ ] No verbatim AI in written documentation

---

## Common reasons teams lose points

1. App not deployed or broken at submission time
2. Design doc missing, shallow, or obviously AI-generated
3. Task board does not match what was built
4. Little or no automated testing
5. Video missing speaking / on-camera / ID requirement for a member
6. Repo not shared with `quantic-grader`
7. “Basic CRUD only” with no clear innovation or engineering story
8. Uneven contribution — hard to defend in video and git history
